Where the Diagrid instructions were wrong, missing or misleading:
1. No guide covers this case: run a plain HTTP agent that doesn't use Dapr, unchanged, and
   call it through Catalyst. The deploy skill stops at "is it ready" and says invoking an
   app "is not available over MCP yet". I had to put the path together myself from the
   service invocation curl in diagrid-app-tunnels section 4.
2. App or Agent is unclear. The deploy skill says code you run yourself uses Agent, but
   "Agent" in these docs mostly means a durable agent that registers itself. Nothing says
   whether an agent like this one, with no Dapr in it, should be an App or an Agent. I chose
   Agent; it worked as a target for service invocation.
3. The console URL is wrong for this org. The skill gives https://catalyst.diagrid.io as the
   only host, and `dev run` printed the same link, but this org is on staging
   (api.staging.diagrid.dev). Nothing gives a console host for staging.
4. Reading the Agent back misleads. diagrid_get_agent reported the Agent "ready" while its
   identity was still "processing" ("missing instances status data") and then "updating".
   The skill warns that ready needs a token, but not that the Agent's own top-level status
   can say ready before its identity is.
5. The Agent added an app config nobody mentioned. Creating it attached
   appConfig "order-agent-lg-1847-agentcfg-50dd503c" to the identity. Neither the schema
   nor the skills say this happens or what the config does. It didn't block the call.
6. The "send the request through Catalyst" step has no caller. Section 4 assumes a second
   caller app. With none, the only route was calling the agent's own identity using its own
   token, which isn't documented as allowed.
7. The `dev run` health check doesn't match what the docs say. The tunnel record shows
   `/healthz` with probing disabled, and the sidecar probed `GET /` and `GET /dapr/config`

   first; here it didn't need to.
8. Small one: `diagrid dev stop` printed "disconnected", but the tunnel record still read
   `status: ready` (with `deletedAt` set) right afterwards. The skill does warn that closing
   takes up to a minute.
